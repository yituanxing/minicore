# Product RV64GC FPGA external-DDR ownership contract (G5-SD1)

Status: **implemented RTL interface, not an FPGA or Debian boot signoff**. The
board-specific PLL, DDR PHY/controller, firmware byte-source transport, pin
constraints, SD wiring and rootfs have not been delivered or qualified by this
source tree. The bounded FW+DTB byte-stream-to-AXI write engine **is** present,
but does not provide its own flash/SD reader or byte source.

## Why the board needs one physical DDR AXI master

The original `AetherCoreProductFpgaColdBootPins` already gated the CPU reset
and isolated its AXI pins until external firmware loading completed, but it
exported only the CPU master and two owner flags. Every board integrator had
to invent an AXI mux; an incorrect AW/W/B or AR/R handoff can corrupt a Debian
boot in a way that takes billions of RTL cycles to diagnose.

The additional `AetherCoreProductFpgaColdBootDdrFabric` is a board-neutral
single DDR port:

* `loaderAxi`: **input** from an external image-loading AXI master;
* `ddrAxi`: **output** to a board-provided 64-bit AXI4 DDR slave/controller;
* `loaderOwnsDdr`, `cpuOwnsDdr`: exclusive handoff grants;
* `loaderDrained`: calculated from accepted AW/W/B and AR/R handshakes, plus
  the absence of new requests; this is not an unverified software assertion;
* `loaderAddressFault`: internal sticky guard; the loader may access only
  the configured physical DDR RAM window, with aligned single-beat transfers.
  Invalid addresses/lengths are denied before the DDR AXI handshake and
  generate a sticky `bootFault` via the existing cold-start controller;
* `loaderIdle`: an independent board loader hint; both `loaderIdle` and
  `loaderDrained` must hold before CPU release;
* `clockLocked`, `ddrCalibrated`, `imageLoaded`, `imageLoadFailed`: synced
  board status inputs, not generated by Product hardware;
* `cpuReleased`, `bootFault`: CPU reset release and sticky fault observability.

The AXI mux selects the loader only while `loaderOwnsDdr`, the CPU only while
`cpuOwnsDdr` and **neither** during the isolation turnaround or faults. AW and
W may handshake separately, so both are accounted for until B is accepted;
each AR is retained until the final R beat. The supplied loader protocol is
single-beat AXI (`len == 0`, `w.last` and `r.last`). A board loader with DMA
bursts needs an explicit width/burst adapter, not a changed unwritten premise.
An after-release DDR/clock fault returns ownership to *neither* side; the
image loader cannot overwrite live CPU memory without a full board reset.
The emitted AXI addresses are **physical** (`0x8000_0000` DDR base). A vendor
controller with a local zero-based AXI port requires a board-owned address
window/offset adapter. It must preserve response ordering, ID semantics,
ready/valid backpressure and exact lane strobes; the owner mux does not
silently remap addresses or data width.

## Actual reset and image ownership sequence

1. Assert board reset; synchronize `clockLocked` and `ddrCalibrated` into the
   Product clock domain. Never drive the Product AXI to an uncalibrated DDR IP.
2. Keep `imageLoaded` **low until after loader grant**. The existing cold-boot
   control deliberately waits to see it low after DDR calibration to reject
   stale loaded states from previous resets.
3. When `loaderOwnsDdr` becomes high, the optional stream engine consumes
   **exactly two** `segment` descriptors: first OpenSBI `fw_payload.bin` at
   physical `0x8000_0000`, then the standalone DTB at `0x87f0_0000`. The FW
   image must end at or before the DTB base; the DTB is limited to 1 MiB.
   Each segment carries its actual `byteCount` and `lastSegment`; low-lane-first
   `wordIn` transfers include `validBytes` (1–8, low bytes in little-endian
   order) and `lastWord`. The engine backpressures the source with
   ready/valid handshakes and bounds both address ranges, rejects malformed
   segments, and converts the final
   partial word into its exact AXI WSTRB mask. The board source still must
   prove the payload identity/hash and provide the bytes. There is no
   SD/flash/UART-reader implementation in this hardware.
4. The optional stream engine waits for the final DTB **B response with OKAY
   status and the expected ID**, then asserts its `imageLoaded` and
   `loaderIdle` together. The mux separately observes its own outstanding
   transactions and prevents a false idle hint from releasing the CPU.
5. A one-clock-ownerless turnaround follows. The CPU reset then releases and
   Product owns DDR. No AXI response can leak into the other owner.
6. Lost PLL lock, DDR calibration or loader error drives sticky `bootFault`
   and isolates CPU traffic. A full board reset is required for a new load.

The existing `AetherCoreProductFpgaColdBootPins` port ABI remains unchanged
for older integrations. G5-SD1's explicit owner mux is opt-in through:

```
./mill aethercore.runMain aethercore.soc.ElaborateProductFpgaColdBootDdrMuxSpiSd1PinsRv64gc small
```

For the joined, synthesizable two-segment firmware stream engine and DDR owner
mux, select the independently named top:

```
./mill aethercore.runMain aethercore.soc.ElaborateProductFpgaColdBootDdrStreamSpiSd1PinsRv64gc small
```

This second top accepts `segment` and `wordIn` via backpressured ready/valid
handshakes; it is not itself a complete board boot ROM or external-media
controller. Both tops leave DDR PHY, board clock/PLL and SD electrical wiring
to the implementation, and both keep the existing ColdBootPins ABI intact.

This is an *emission example*, not evidence that the command was run. The
same CPU source supports `expanded` single-lane geometry. A matching device
tree must be generated with `EmitAetherSoCDts --spi-sd`, with the actual board
clock and SPI limits reflected in the SPI node's `clock-frequency`.

## Persistent Linux rootfs belongs on SD, not in the boot payload

The D3 native `/sbin/init` experiment embeds a full rootfs in an initramfs.
Its legacy memory layout has only 256 MiB RAM, and firmware must fit below
the device tree at `0x87f0_0000` (about 127 MiB from the image base). Neither
the FPGA owner mux nor this note increases that budget.

G5-SD1 must keep boot firmware + Linux Image + DTS small, load those from an
external image source into DDR, and put the complete Debian LP64D rootfs on
the physical SPI SD card. The Linux kernel needs **built-in**
`CONFIG_SPI_OC_TINY`, `CONFIG_GPIO_ALTERA`, `CONFIG_MMC_SPI`, `CONFIG_MMC_BLOCK`
and `CONFIG_EXT4_FS`, plus an exact device tree and bootargs selecting the
real SD partition (with `rootwait`/`rootfstype=ext4`). This is a separate
software artifact ownership requirement; the board must actually wire the
SD card's 3.3V MISO/MOSI/SCK/CS and match chip-select polarity.

The architecture roadmap's `D4` remains the **CPU performance** milestone;
this SD-root qualification is deliberately named `G5-SD1` instead.

Do not claim a successful distro boot based on RTL generation, DTS presence,
`/sbin/init` handoff from an initramfs, or QEMU simulation. Final qualification
requires a real board's DDR/PLL/SD electrical constraints, bootloader image
identity, serial `/sbin/init` and login, and a persistent file surviving reboot.
